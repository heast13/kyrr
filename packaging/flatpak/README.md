# Flatpak

The Flatpak of kyrr, written for a later submission to Flathub.

| File | What it is |
| --- | --- |
| `io.github.heast13.kyrr.yml` | The manifest: ONNX Runtime, sherpa-onnx (from source, without text-to-speech) and kyrr (from source, offline) |
| `cargo-sources.json` | Every crate in `Cargo.lock` as a download with its SHA256, generated by `flatpak-cargo-generator` |
| `flathub.json` | Builds on x86_64 only (see "Architectures") |
| `flathub.py` | Writes the three files Flathub gets for a release (or a commit) |

Desktop file, MetaInfo and icons are not copied here; the manifest installs
the shared ones from `packaging/linux/` and `crates/kyrr-app/ui/icons/`.

Runtime: `org.freedesktop.Platform` 26.08 with the SDK extensions
`rust-stable` (Rust 1.98) and `llvm22` (libclang for bindgen in
pipewire-sys). Update all three together when a new Freedesktop branch comes
out in August.

## Building locally

Needs `flatpak` and the `org.flatpak.Builder` Flatpak, about 6 GB for the
runtime, SDK and extensions and about 6 GB for the build.

```sh
flatpak remote-add --user --if-not-exists flathub https://dl.flathub.org/repo/flathub.flatpakrepo
flatpak install --user flathub org.flatpak.Builder

# The working tree, from the repository root. Build and repo folders outside
# the repository, or they would be copied into the build as part of the app
# source.
flatpak run --command=flatpak-builder org.flatpak.Builder --user --force-clean \
  --install-deps-from=flathub --repo=$HOME/.cache/kyrr-flatpak/repo --install \
  $HOME/.cache/kyrr-flatpak/build packaging/flatpak/io.github.heast13.kyrr.yml

flatpak run io.github.heast13.kyrr
```

The app source is `type: dir` with `path: ../..`, the working tree as it is
(minus `target/`, `.git/`, `assets/` and flatpak-builder's own folders). The
noise models come from the manifest's own `file` sources, not from `assets/`.
`flathub-build` (Flathub's own command) builds sandboxed and does not accept
a source outside the manifest's folder; it is for the files `flathub.py`
writes, which take kyrr from GitHub:

```sh
python3 packaging/flatpak/flathub.py "$(git rev-parse HEAD)" /tmp/kyrr-flathub   # a pushed commit
cd /tmp/kyrr-flathub
flatpak run --command=flathub-build org.flatpak.Builder --install io.github.heast13.kyrr.yml
lint() { docker run --rm -v "$PWD":/mnt ghcr.io/flathub/flatpak-builder-lint:latest --permission-review "$@"; }
lint manifest /mnt/io.github.heast13.kyrr.yml
lint repo /mnt/repo
```

The linter runs from Flathub's own image, which follows the linter's main
branch as Flathub's checks do; the one inside `org.flatpak.Builder` can be
a release behind and lack `--permission-review`.

`.github/workflows/flatpak.yml` does exactly this for every pull request that
touches the packaging, and offers the result as the bundle `kyrr-flatpak`
(`flatpak install --user kyrr.flatpak`). `--permission-review` reports the
permissions that need Flathub's review (see "Permissions") as warnings
instead of errors.

### What the build does

1. **onnxruntime**: Microsoft's release archive, installed as
   `/app/lib/libonnxruntime.so.1` plus headers (headers are removed at the
   end by `cleanup`).
2. **sherpa-onnx** 1.13.8 from its git tag, CMake, static libraries,
   `SHERPA_ONNX_ENABLE_TTS=OFF` (no espeak-ng, no piper-phonemize) and
   speaker diarization off. Its CMake fetches dependencies with
   FetchContent, but looks for the archives in its source folder first and
   checks them against the same SHA256; the manifest puts them there as
   `file` sources (kaldi-native-fbank, kissfft, kaldi-decoder, kaldifst,
   openfst, eigen, simple-sentencepiece, nlohmann json). The environment
   variables `SHERPA_ONNXRUNTIME_INCLUDE_DIR` and `SHERPA_ONNXRUNTIME_LIB_DIR`
   make it use the ONNX Runtime above instead of downloading its own.
   Installed to `/app/sherpa-onnx`, which `cleanup` removes again: nothing of
   it ships except what is linked into `kyrr`.
3. **kyrr**: `cargo --offline build --release --locked -p kyrr` with
   `SHERPA_ONNX_LIB_DIR=/app/sherpa-onnx/lib`. sherpa-onnx-sys always links
   `espeak-ng`, `piper_phonemize`, `ucd` and `onnxruntime` as static
   libraries; the first three are empty archives as in
   `scripts/fetch-assets.py`, and so is `libonnxruntime.a`, because ONNX
   Runtime is the shared library here. `RUSTFLAGS` adds
   `-lonnxruntime` at the end of the link line, where the references from
   the sherpa-onnx archives resolve against `/app/lib/libonnxruntime.so`.
   Then the models go to `/app/share/kyrr` (`engine.rs` `assets_dir()`), the
   notices to `/app/share/doc/kyrr` (`platform.rs` `open_licenses()`, crate
   licenses through `scripts/collect-licenses.py`), and license files of all
   three modules to `/app/share/licenses/io.github.heast13.kyrr/`. ONNX
   Runtime's `LICENSE` and `ThirdPartyNotices.txt` also go to
   `/app/share/doc/kyrr/licenses/` as `LICENSE-onnxruntime.txt` and
   `ThirdPartyNotices-onnxruntime.txt`, the same names as in the AppImage and
   tarball (`scripts/package-linux.py`).

## Regenerating cargo-sources.json

After every change to `Cargo.lock`:

```sh
git clone https://github.com/flatpak/flatpak-builder-tools
python3 -m venv /tmp/fct && /tmp/fct/bin/pip install aiohttp tomlkit PyYAML
/tmp/fct/bin/python flatpak-builder-tools/cargo/flatpak-cargo-generator.py \
  Cargo.lock -o packaging/flatpak/cargo-sources.json
```

It lists every package in the lock file, the Windows-only ones included, so
it does not depend on the platform it runs on.

## Updating sherpa-onnx

`sherpa-onnx` is pinned in `crates/kyrr-dictate/Cargo.toml` (`=1.13.8`).
When it moves: change `tag` and `commit` of the sherpa-onnx git source, then
compare the `file` sources with the new tag's `cmake/kaldi-native-fbank.cmake`,
`kaldi-decoder.cmake`, `openfst.cmake`, `eigen.cmake`,
`simple-sentencepiece.cmake`, `json.cmake` and the nested ones
(`cmake/kissfft.cmake` of kaldi-native-fbank, `cmake/kaldifst.cmake` of
kaldi-decoder). `python3 cmake/download-all-deps.py` in the sherpa-onnx tree
lists them all. The file names (`dest-filename`) must be exactly the ones
the cmake files look for. Check `SHERPA_ONNX_STATIC_LIBS` in the new
`sherpa-onnx-sys` `build.rs` for libraries that need a stand-in, and the
ONNX Runtime version in `cmake/onnxruntime-linux-x86_64.cmake`.

## For the Flathub submission

Checked against Flathub's requirements (docs.flathub.org, 2026-10-21): the
technical side is green (build and linter in the CI run on `main`, metainfo, app ID), the policy side
is not. Open points, in the order they matter:

1. **Generative AI policy.** Flathub manifests must not contain
   AI-generated or AI-assisted content, AI-generated code and packaging
   must be disclosed with the affected parts and approximate extent, and
   AI tools must not open the submission pull request or write its
   description, commit messages or replies. The manifest, `flathub.py` and
   this folder were written with Claude, as was most of kyrr. The
   submission itself is therefore a by-hand job: the person submitting
   writes the manifest and the pull request, discloses honestly, and
   reviewers may still reject on the extent.
2. **Development history.** "Applications that have only existed for a very
   short period of time will generally not be accepted"; they want a
   sustained history, tagged releases, real-world use and committed
   maintenance. kyrr's first release was 2026-10-10.
3. **The compositor socket link** (see "Typing on tiling compositors")
   hands the app the unfiltered Wayland socket, which is a bypass of the
   security context. Flathub does not accept "disabling or bypassing
   security mechanisms", and does not grant permission exceptions that are
   only needed on one narrow environment (the four `xdg-config/*` folders
   exist only for Hyprland, sway, niri and river). A Flathub build without
   the link and without those four folders works on GNOME and KDE through
   portals; on tiling compositors typing and the dictation key then need
   the AppImage or AUR package.
4. ONNX Runtime is a prebuilt binary (README, "Open points for review").
5. Screenshots must be taken on Linux, of the window with its shadow, at
   most 1000x700 (2000x1400 on HiDPI), in the current state of the UI.
   Nothing to fix in the files until they exist.

What is in place: the app ID `io.github.heast13.kyrr` follows the rules
(GitHub prefix, four components, repository `heast13/kyrr` reachable,
verification through the GitHub login of the repository owner), the
metainfo matches the licenses in the source and passes the linter, the
manifest builds from a git tag and commit with offline cargo sources, and
the runtime is the current Freedesktop branch.

The steps, once the points above are settled:

1. Tag a release that has the commits of this folder; its `<release>` is the
   newest one in the metainfo and the screenshot URLs name that tag or a
   commit (`flathub.py` checks both; a branch is refused).
2. `python3 packaging/flatpak/flathub.py 0.X.Y /tmp/kyrr-flathub` writes the
   three files Flathub gets (as a reference for the by-hand manifest, see
   point 1): the manifest with the `type: dir` source swapped for the
   release's `tag` and `commit`, and that tag's `cargo-sources.json` and
   `flathub.json`.
3. Build and lint them with `flathub-build` and `flatpak-builder-lint` as
   under "Building locally".
4. The pull request against `flathub/flathub` (base branch `new-pr`) is made
   by the maintainer with the repository's template filled in, a video of
   the Flatpak on Linux, and only these three files, side by side at the
   top level. Its description explains the permissions that need review
   (see "Permissions").
5. After the app is accepted, the ID is verified on Flathub through the
   GitHub account `heast13`. Later releases go to the app's own repository
   `flathub/io.github.heast13.kyrr` the same way (`flathub.py`, then a pull
   request with the three files).

## Permissions

| Permission | Why |
| --- | --- |
| `--socket=wayland`, `--socket=fallback-x11`, `--share=ipc` | The window; X11 only without Wayland, IPC for X11 shared memory |
| `--share=network` | Speech model download on first dictation, "Check for updates" |
| `--filesystem=xdg-run/pipewire-0:ro` | The virtual microphone: a PipeWire source node and the default-source setting. As EasyEffects on Flathub. There is no portal for creating audio devices |
| `--socket=pulseaudio` | cpal records and plays through ALSA, and ALSA's default device in the Freedesktop runtime is the PulseAudio plugin (`/etc/alsa/conf.d/99-pulseaudio-default.conf`). Dictation, listening to yourself and the before/after test need it |
| `--talk-name=org.kde.StatusNotifierWatcher` | The tray icon (see "Tray icon") |
| `--filesystem=xdg-config/hypr`, `sway`, `niri`, `river` | Tiling compositors have no portal dialog for keys or autostart. kyrr writes its dictation key, and the start at sign-in when asked, into the compositor's config between its own marker lines, and the same block links the compositor's socket for typing (see "Typing on tiling compositors"). Each folder is used only on its own compositor |

`flatpak-builder-lint --permission-review` flags the four `xdg-config`
folders for review; the table row above is the answer. Portals cover the
rest without static permissions: GlobalShortcuts (the push-to-talk key on
GNOME and KDE), RemoteDesktop (typing where the Wayland virtual keyboard is
not offered), Background (autostart on GNOME and KDE), OpenURI (links and
the license file).

## How the sandbox is handled

### Typing on tiling compositors

Hyprland, sway, niri and river give a Flatpak a Wayland socket with a
security context (`wp_security_context_v1`), and on that socket they hide
the privileged protocols: the virtual keyboard (typing), layer surfaces (the
dictation wave) and data control (the clipboard). None of them offers the
RemoteDesktop portal either (xdg-desktop-portal-wlr and -hyprland have no
keyboard input).

The compositor's own socket has no such filter, and the app's runtime folder
`$XDG_RUNTIME_DIR/app/io.github.heast13.kyrr/` is the same folder inside and
outside the sandbox. So kyrr's block in the compositor config also starts

```sh
mkdir -p "${XDG_RUNTIME_DIR}/app/io.github.heast13.kyrr" && ln -f "${XDG_RUNTIME_DIR}/${WAYLAND_DISPLAY}" "${XDG_RUNTIME_DIR}/app/io.github.heast13.kyrr/wayland"
```

when the compositor starts and on each config reload (`exec` in Hyprland,
`exec_always` in sway, a line in river's init), on niri before each start of
the dictation key, and `crates/kyrr-linux/src/display.rs` connects to that
hard link first.

What this hands over: the compositor's own socket, with every protocol the
compositor offers, the privileged ones included; the security context is
gone for this app. It happens only through the user's compositor config,
which kyrr writes when the user sets up its key there, and only on these
four compositors. Without the link (before the key is set, or on a
compositor kyrr does not know), typing and the clipboard both fail in the
sandbox, and the app says that the AppImage can type there.

### Tray icon

Slint's tray (ksni 0.3) claims `org.kde.StatusNotifierItem-<pid>-<n>` on
the session bus, which a Flatpak may not own (Flathub rejects
`--own-name=org.kde.*`). `vendor/ksni` is ksni 0.3.6 with one line changed:
in a Flatpak it registers under its unique bus name instead, which the
StatusNotifier spec allows and every tray host reads
(`vendor/ksni/PATCHES.md`, remove once Slint ships `disable_dbus_name`).

### Handled in the app

- Default microphone: PipeWire gives Flatpak clients read and execute only,
  unless they set `media.category = "Manager"` (as EasyEffects and Helvum
  do). `crates/kyrr-linux/src/mic.rs` connects that way, so the write to the
  `default` metadata works.
- Autostart: on GNOME and KDE the Background portal (`RequestBackground`,
  `autostart`, `["kyrr", "--background"]`); on tiling compositors the line
  in their config, as for the native app.
- Second start: `$XDG_RUNTIME_DIR` is private to each running instance of a
  Flatpak; `crates/kyrr-linux/src/instance.rs` puts its socket in the shared
  `$XDG_RUNTIME_DIR/app/$FLATPAK_ID/` there, so
  `flatpak run io.github.heast13.kyrr --dictate` reaches the running kyrr.
- Update check: "Check for updates" only reads GitHub's latest release; on
  Linux there is no "Update now", the note says to update where kyrr was
  installed from.

## Open points for review

### ONNX Runtime is a prebuilt binary

Flathub wants everything built from source. ONNX Runtime is the exception
here: the module uses Microsoft's official release archive
(`onnxruntime-linux-x64-1.28.2.tgz`, the version sherpa-onnx 1.13.8 is built
with). Other apps on Flathub do the same, for example `net.mkiol.SpeechNote`
(module `onnx`, Microsoft's 1.16.1 archive) and
`com.obsproject.Studio.Plugin.BackgroundRemoval` (Microsoft's 1.23.2
archive). `flathub/shared-modules` has no ONNX Runtime module. Reviewers may
still ask for a source build or grant it as a well-known-vendor exception.

Plan B, an `onnxruntime` source module that replaces the archive and still
installs `/app/lib/libonnxruntime.so.1` and the headers, so the other two
modules stay as they are:

- source: `type: git`, `https://github.com/microsoft/onnxruntime.git`, tag
  `v1.28.2` and its commit; `buildsystem: cmake-ninja`, `subdir: cmake`,
  `builddir: true`
- every entry of the tag's `cmake/deps.txt` that a CPU-only Linux build
  uses (abseil_cpp, date, eigen, flatbuffers, fp16, fxdiv, json,
  microsoft_gsl, mp11, onnx, protobuf, psimd, pthreadpool,
  pytorch_cpuinfo, re2, safeint, googlexnnpack/kleidiai only if enabled) as
  an `archive` source with `dest` set and
  `-DFETCHCONTENT_SOURCE_DIR_<NAME>=...` per dependency, plus
  `-DFETCHCONTENT_FULLY_DISCONNECTED=ON`; `protoc_linux_x64` is a prebuilt
  protoc, so protoc has to come from the protobuf source instead
  (`-DONNX_CUSTOM_PROTOC_EXECUTABLE=` or building protobuf first)
- flags: `-Donnxruntime_BUILD_SHARED_LIB=ON -Donnxruntime_BUILD_UNIT_TESTS=OFF
  -Donnxruntime_ENABLE_PYTHON=OFF -Donnxruntime_USE_XNNPACK=OFF
  -Donnxruntime_ENABLE_CPUINFO=ON -Donnxruntime_BUILD_BENCHMARKS=OFF
  -DCMAKE_BUILD_TYPE=Release`
- cost: a long C++ build (roughly an hour and several GB of RAM per job on
  Flathub's builders); set `-j` low enough or add
  `build-options: { cflags: -g1 }` if memory runs out.

### PipeWire and PulseAudio permissions in app stores

GNOME Software and the Flathub website list `--filesystem=xdg-run/pipewire-0`
as file system access and may rate the app's permissions "potentially
unsafe"; `--socket=pulseaudio` shows as microphone and speaker access. Both
are needed for what the app does; the review comment should say so. Moving
dictation recording and playback from cpal's ALSA backend to its PipeWire
backend (cpal feature `pipewire`) would make `--socket=pulseaudio`
unnecessary.

### Slint license and `project_license`

`project_license` is `MIT OR Apache-2.0`, the license of kyrr's own source,
and Flathub asks that it match the license information in the source. That
holds. The binary links Slint, which kyrr uses under the Slint Royalty-free
Desktop, Mobile and Web Applications License 2.0 (Slint itself is
`GPL-3.0-only OR LicenseRef-Slint-Royalty-free-2.0 OR LicenseRef-Slint-Software-3.0`).
Flathub's guidelines do not ask to list licenses of linked libraries in
`project_license` (no app lists its whole dependency tree), so `MIT OR
Apache-2.0` is the expected value. If a reviewer wants the non-OSI component
visible, the expression would be
`(MIT OR Apache-2.0) AND LicenseRef-Slint-Royalty-free-2.0`, and GNOME
Software would then no longer show the app as free software. The
royalty-free license requires attribution, either the "Made with Slint"
badge on the download page or the `AboutSlint` widget in the app. The
website's download section has the badge; the Flathub app page cannot, so
an `AboutSlint` in kyrr's About section would cover that channel too (not
there yet).

### Architectures

x86_64 only (`flathub.json`): Microsoft's ONNX Runtime archive and the
sherpa-onnx build here are x86_64. On x86_64 CPUs without AVX2 the noise
filter falls back from the native DPDFNet engine to the shipped
`/app/lib/libonnxruntime.so.1` (`engine.rs` `onnx_runtime()`), about half
as fast but still well inside its 10 ms per block.
